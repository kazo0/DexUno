# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

DexUno is a Pokémon GO pokedex app. The repo holds two generations of it side by side:

- `DexUno.Modern/` — the **current** app: an Uno Platform single-project app on the `Uno.Sdk` (`-dev` channel), .NET 10, Material theme, MVUX (Uno.Extensions.Reactive) with `FeedView`, Uno.Extensions navigation. Work here unless a task is explicitly about the legacy code. See "Modern app" below.
- `DexUno.sln` + `DexUno/` + `DexUno.Core/` — the **legacy** 2020-era port of the original UWP app ("Dex") to Uno 3.x. Kept for reference; it does not build on current tooling. See "Legacy app" below.

There are no tests in either. The modern app has CI and a release pipeline (GitHub Actions, see "CI, versioning and releases" below); the legacy app is never built or shipped.

## Hard rules

**Never use the owner's admin rights to bypass branch protection.** The `master` ruleset (`docs/RELEASE-SETUP.md` §4) requires a pull request with the five CI checks green and one approving review, and blocks deletion and force-push; a `release branches` ruleset for `release/**` is documented there too. Repository admins have a pull-request bypass (the owner cannot approve their own PRs), so `gh pr merge --admin` succeeds for the owner; treat that as forbidden, not as permitted-because-it-worked. The path is always branch → pull request → checks go green → the owner merges. If that path is blocked, stop and say so.

## Modern app (`DexUno.Modern/`)

Layout:
- `DexUno.Modern.sln`, `global.json` (pins `Uno.Sdk`; bump the version there, never in csproj), `Directory.Packages.props` (central package management, currently empty because the Uno.Sdk supplies implicit packages).
- `DexUno.Modern.Core/` — net10.0 class library, no UI dependencies. `Entities` (records/classes shaped for `System.Text.Json`: `Pokemon`, `Move`→`QuickMove`/`ChargeMove`, `CombatStat`, `CP`, `CpCalculator`, `TypeEffectiveness`, `EvolutionLine`), `DataAccess/IPokedexDataSource` (the single abstraction over the bundled data), `Repositories` (singleton, lazily cached: Pokémon, moves, evolutions) and `Services/TypesService` (type chart, 1.25 / 0.8 multipliers).
- `DexUno.Modern/` — the Uno app. `Platforms/*` heads are template-generated; app code lives in `Presentation/` (pages + MVUX models + a few view-model partials), `Services/` (data source, image lookup), `Converters/`, `Styles/`, `Data/` (JSON, embedded resources), `Assets/Pokemon/` (256px PNGs for #1–151 plus `unknown.png`).

Build / run (from `DexUno.Modern/DexUno.Modern/`, always build a csproj from its own folder):

```bash
dotnet build -f net10.0-desktop          # Skia desktop (macOS/Linux/Windows) — the fast inner loop
dotnet run   -f net10.0-desktop          # launch it
dotnet build -f net10.0-browserwasm      # WebAssembly
dotnet build -f net10.0-ios / net10.0-android   # need the matching workloads
```

Building a single platform: passing `-f` alone still makes **restore** resolve every TFM, which needs every workload. `TargetFrameworkOverride` (platform suffixes `android`, `ios`, `wasm`, `desktop`, semicolon-separated) narrows the csproj's `TargetFrameworks` itself, so restore and build only see the platforms you asked for: `dotnet build -f net10.0-desktop -p:TargetFrameworkOverride=desktop`. It is also read from the environment (each CI job pins itself with `env: TargetFrameworkOverride: <platform>`) and from an optional git-ignored `DexUno.Modern/crosstargeting_override.props` (copy the `.sample`; imported by `Directory.Build.props`). Unset means all four.

There is no WinAppSDK (`net10.0-windows10.0.*`) target: Windows is served by the Skia desktop head, like macOS and Linux. A wasm `dotnet publish` needs the `wasm-tools` workload (on this machine `dotnet` lives in `/usr/local/share/dotnet`, so `sudo dotnet workload install wasm-tools`); a plain wasm `build` does not. The iOS head's minimum OS is pinned to 15.0 in the csproj (`SupportedOSPlatformVersion`, iOS TFM only) because the iOS 27 SDK (Xcode 27) rejects the Uno.Sdk default of 14.2. With that workload the SDK expands the TFM to `net10.0-ios27.0`, so `-f net10.0-ios` fails with NETSDK1005 ("assets file doesn't have a target"); check `dotnet msbuild -getProperty:TargetFrameworks` and pass the expanded name. Both desktop and wasm builds are verified clean on macOS. Restore of a new `-dev` Uno.Sdk version can take several minutes the first time. Uno Platform Studio / Hot Reload attach automatically in Debug through the DevServer.

Architecture:
- **Hosting & DI.** `App.xaml.cs` builds the Uno.Extensions host: logging, `ConfigureServices` (data source, repositories, `ITypesService`, all singletons) and `UseNavigation(ReactiveViewModelMappings.ViewModelMappings, RegisterRoutes)`. The mappings object is generated by MVUX and lets navigation instantiate the generated `*ViewModel` for a `*Model`. Models are resolved by the navigation framework, so their (record primary) constructors take services plus, for detail pages, the navigation data object.
- **Navigation is route/region based (Uno.Extensions).** Routes in `RegisterRoutes`: `""` (Shell) → `Main` (`MainPage`, the responsive shell) → nested visibility regions `Pokedex`, `Movedex`, `Types`, `Search`, `About`; plus root-level `PokemonDetail` and `MoveDetail` which are pushed on the frame from any region. `ViewMap`/`DataViewMap`/`FindByViewModel` all reference the **model** type (`PokedexModel`), never the generated view model. `MainPage.xaml` hosts a `NavigationView` (≥700px) and a bottom `TabBar` (<700px) that share the same `uen:Region.Name`s; the content grid with `Region.Navigator="Visibility"` must stay empty. Around them sits the Pokédex hardware: `PokedexTopStrip` (a shared user control — blue lens, three LEDs, the app title and the plate's notched outline; also placed above the `NavigationBar` of both detail pages so the phone keeps it while a detail is pushed), a `Hinge` gradient strip between the red pane and the content, and a grey `Bezel` grid (two red dots above, red button and speaker grille below) whose inner `Screen` border, on `BackgroundBrush`, holds the region grid. The `Narrow` state collapses the hinge and zeroes the bezel so phones get the full width; `Normal`/`Wide` show the hinge. Keep the ornaments purely decorative — no hit-testing, no layout dependence from the pages. Every `VisualState` in that shell's group needs its own `StateTrigger`, including the narrowest one (`<AdaptiveTrigger MinWindowWidth="0" />`): a trigger-less state is never entered, the group falls back to base property values, and the `TabBar` silently stays collapsed. Adding a section = page + model + `ViewMap` + `RouteMap` + one `NavigationViewItem` and one `TabBarItem`.
- **Status bar / safe area.** One `utu:SafeArea.Insets="VisibleBounds"` on the `Shell` root `Border` covers every page, including the detail pages pushed over the shell (the pages' own `SafeArea` attributes predate it and are harmless). The toolkit's `SafeArea` has a bug on near-square displays: it refuses to apply insets while `Window.Bounds` and `ApplicationView.VisibleBounds` differ in orientation (meant to ride out rotation), and a fold's inner screen is permanently in that state (852×883 window vs 852×795 visible), so nothing gets padded. `Shell.xaml.cs` pads the root itself on Android in exactly that case, mirroring the toolkit's orientation rule; when the orientations agree SafeArea owns the padding. Don't add more `SafeArea` workarounds per page — fix it at the root or upstream.
- **Detail pages take data via `DataViewMap`.** `PokemonDetailModel(Pokemon?, …)` and `MoveDetailModel(MoveSelection?, …)`. `MoveSelection` is a sealed wrapper because moves are polymorphic and route/data matching is by type; keep using it rather than passing `Move` directly. Navigate from a model with `Navigator.NavigateViewModelAsync<TModel>(this, data: …, cancellation: ct)`.
- **Master/detail is a hinge-aware `TwoPaneView`.** `PokedexPage`/`MovedexPage` put the list in `Pane1` and the detail in `Pane2` of a `TwoPaneView` (`MinWideModeWidth="900"`, `MinTallModeHeight="1200"`, `PanePriority="Pane1"`): side by side on wide pages, stacked on very tall ones, and — through the `Foldable` UnoFeature (`Uno.WinUI.Foldable`) — along the hinge of a spanned dual-screen device whatever its size, so the hinge never cuts through a pane. That package only has real code for Android (the other TFMs get an empty stub). It reports spanning only when Jetpack's `FoldingFeature.isSeparating` is true — an occluding hinge (Surface Duo) or a single-display foldable in the HALF_OPENED posture — so a flat foldable would fall through to the size thresholds and the seam would sit beside the crease rather than on it. As shipped (6.8.0-dev.130) it does not work on its own either, which is what `Platforms/Android/HingeAwareSpanningRects.cs` is for — a subclass of its provider registered from a `[ModuleInitializer]` that treats a fold in any posture as spanning (Jetpack still reports its bounds when flat) and fixes three things, each verified on the fold emulator: (1) the generated `ApiExtensibility.Register` lands in `App.InitializeComponent`, but on Android `App` is constructed after `MainActivity`, and `BaseActivity`'s constructor creates the `ApplicationView` which looks the extension up once and caches "none", so the stock provider never exists; (2) the stock `GetSpanningRects` compares the fold's Y with `VisibleBounds.Y` (status-bar offset) and returns nothing for a vertical fold; (3) it never notifies anyone of a posture change, and `TwoPaneView` only re-evaluates on size/XamlRoot changes. The subclass re-implements `IApplicationViewSpanningRects.GetSpanningRects` from Jetpack's window bounds and adds a second `WindowLayoutInfo` listener that raises the shared `FoldPosture.Changed`; `PokedexPage`/`MovedexPage` answer it with `FoldPosture.Refresh(Panes)`, which nudges `MinTallModeHeight` because that is a public property whose change calls the private `UpdateMode`. Don't move that registration into `App` or `MainActivity` — both run too late. On the emulator, `adb shell cmd device_state state 1` (HALF_OPENED) / `state reset` switches posture; give a Debug build ~15 s to re-layout. The code-behind handles `ModeChanged` and calls `vm.Model.SetTwoPane(mode != SinglePane)` (and flips the divider `BorderThickness` for Tall). Don't reintroduce a width breakpoint of your own: `TwoPaneView` already accounts for where the page sits on screen relative to the hinge. The list model owns a child `PokemonDetailModel`/`MoveDetailModel` (`DetailModel`, created with a null initial item so its `Current` state starts empty). With two panes showing, selecting an item calls `DetailModel.Show(...)` and the pane shows it through the shared `PokemonDetailView`/`MoveDetailView` user controls; with a single pane, selection navigates to the detail page. The MVUX generator exposes nested models as raw pass-throughs, so `PokedexViewModel.cs`/`MovedexViewModel.cs` are hand-written partials of the generated view models that expose a bindable `Detail` built through the generated `protected XViewModel(XModel)` constructor (`PokemonDetailViewModel.For(...)`). Those partials carry `[ReactiveBindable(false)]` because their names end in `Model` and would otherwise be treated as models themselves. The legacy app's `TwoPaneView` + `Uno.UI.DualScreen` spike was the same idea.
- **MVUX.** `UnoFeatures` includes `MVUX`; no CommunityToolkit.Mvvm. Every page has a `partial record XxxModel` whose services come in as record primary-constructor parameters; the generator emits `XxxViewModel` (what the page's `DataContext` actually is) with a `Model` property. Async data is exposed as `IFeed<T>`/`IListFeed<T>` (`Feed.Async`, `ListFeed.Async`, `state.Select/SelectAsync`, `Feed.Combine(...)...AsListFeed()`), user input as `IState<T>` (`State.Value(this, () => …)`, two-way bound; update with `UpdateAsync`), and public methods become `IAsyncCommand`s of the same name (`ToggleSortDirection`, `SelectPokemon(Pokemon, ct)` → item is the command parameter). Read a feed's current value with `await SomeFeed`. Nothing loads in constructors; feeds load when the view subscribes. Records like `PokemonDetails`/`MoveDetails` carry what a detail view shows; a feed's `null` result or an empty list feed is the `None` state. Avoid naming anything that is not a model with a `Model` suffix.
- **Lists are ItemsRepeaters, and the long ones are paginated.** No `ListView` anywhere: every list is an `ItemsRepeater` inside a `ScrollViewer` (`DexListScrollViewerStyle`), with `utu:ItemsRepeaterExtensions.SupportsIncrementalLoading="True"` where the feed is paginated, `utu:ItemsRepeaterExtensions.SelectionMode`/`SelectedItem` for the master lists' highlight (two-way bound to a `Selected` state on the model) and `utu:CommandExtensions.Command` for the tap action. Selection visuals need the item template's root to be a `ListViewItem` (or another `SelectorItem`/`ToggleButton`) — that is why `PokemonListItemTemplate`/`MoveListItemTemplate` wrap their row in one; the toolkit sets `IsSelected` itself, don't bind it.
  Paginated feeds: `PokedexModel.Items`, `MovedexModel.Items`, `SearchModel.Results` and `MoveDetailModel.UsedBy` (a common move has a hundred users, and it pages in as the detail view is scrolled). Each is `<source feed>.SelectPaginatedAsync<…, T>((value, page, ct) => …)`, slicing a cached filtered/sorted list with `page.CurrentCount`/`page.DesiredSize` (`DefaultPageSize` only covers the first page, where `DesiredSize` is null), and restarts from page 1 whenever the source value — search text, sort, tab, current move — changes. The private `MatchesAsync`/`UsersAsync` caches exist so a page request is a slice, not a re-query. The Types list (18 cards) is an `ItemsRepeater` without pagination.
  The scroller keeps its offset when the criteria change, which would leave a shorter result set rendering as blank space, so `PokedexPage`/`MovedexPage`/`SearchPage` capture the `ScrollViewer` from inside the FeedView template (`Loaded`) and scroll it back to the top from the search / tab / reverse-order handlers.
- **FeedView everywhere.** All async content is rendered through `mvux:FeedView Source="{Binding SomeFeed}"` (`xmlns:mvux="using:Uno.Extensions.Reactive.UI"`). Inside its templates the `DataContext` is the `FeedViewState`: bind values as `{Binding Data.…}`, commands as `{Binding Parent.SomeCommand}`, and reach the view model from nested item templates with `{Binding DataContext.SomeCommand, ElementName=<named root>}`. `NoneTemplate` is used for empty lists, the blank search query and the unselected master/detail pane. The loading visual is the animated pokeball `PokeballLoader` user control (a vector copy of `unknown.png` with a wobble/button-flash storyboard): an implicit `FeedView` style in `AppResources.xaml` sets it as every `ProgressTemplate`, and the splash screen in `Shell.xaml` uses it too, so never add a `ProgressRing`. `Shell.xaml` sets `ExtendedSplashScreen.Platforms="None"` so the toolkit does not replicate the native splash image/colour: the extended splash is just the centred pokeball on `BackgroundBrush`. List item taps are wired with `utu:CommandExtensions.Command` on the `ItemsRepeater` (item = command parameter), never in code-behind. Inside a `NoneTemplate`, `{Binding Parent.…}` does not resolve — reach the view model through the page's named root instead (`{Binding DataContext.SearchText, ElementName=Root}`, as `SearchPage` does for its two empty states).
- **Data.** `Data/*.json` are `EmbeddedResource`s (`Data.<name>.json`) read by `EmbeddedJsonPokedexDataSource` through a source-generated `PokedexJsonContext` (case-insensitive, string enums). Type chart JSON keys are the attacking type; `strengths`/`weaknesses` map to `StrongAgainst`/`WeakAgainst`.
- **Theme & resources.** The Material 3 palette is *generated* from three seed colours sampled from the classic Kanto Pokédex, set on `ThemeColors` inside `MaterialToolkitTheme` in `App.xaml`: `PrimarySeed` body red `#DC0A2D`, `SecondarySeed` lens blue `#28AAFD` (selected pills in the nav pane and bottom tabs), `TertiarySeed` button green `#51AE5F`. The theme's HCT generator (default `SeedColorMode` Fidelity: light Primary is the seed itself, dark Primary is tone 80, neutrals take a low-chroma tint of the seed hue) derives every other role for both themes. `Styles/ColorPaletteOverride.xaml` is wired through `ThemeColors.OverrideSource` (the old `ColorOverrideSource` on the theme is obsolete) and holds only deliberate deviations from the generated palette — currently just dark `PrimaryColor`/`OnPrimaryColor` pinned to the body red and white, so the chrome stays Pokédex red at night instead of the generated pale red. Add a colour there only when the seeds cannot produce what you need. Because that dark red is only ~3:1 on dark surfaces, small red text (card section titles, the headline numbers, the evolution buttons) uses `DexAccentBrush` — a theme brush in `AppResources.xaml`, body red in light and a lighter red in dark — never `PrimaryBrush` directly. `PokedexRedBrush` (non-theme) is the same red for surfaces that must be it in every theme: the `Shell` root behind the safe-area insets. Chrome: every page's `NavigationBar` uses the toolkit's `PrimaryNavigationBarStyle`, the Pokédex/Movedex tabs sit directly under it in `ColoredTopTabBarStyle` (search box below the tabs), and the `NavigationView` pane and the bottom `TabBar` in `MainPage.xaml` are the same red through lightweight styling: their `Resources` re-point the Material template keys (`NavigationViewDefaultPaneBackground`, `NavigationViewItemBackgroundSelected`, `NavigationTabBarItemActiveIndicatorBackgroundSelected`, the hover/pressed state layers, …) at `PokedexRedBrush`, `PokedexRedDarkBrush` (the selected pill) and the `OnPokedexRed*` white brushes from `AppResources.xaml`. Item text colour and the `TabBar` background are *style setters* in those templates, which lightweight resources cannot reach, so each `NavigationViewItem`/`TabBarItem` carries an explicit `Foreground` and the `TabBar` an explicit `Background`; the three pages the frame shows (`MainPage`, both detail pages) set `utu:StatusBar.Foreground="Light"` because the status-bar strip is red. Stat gauges are the Pokédex's indicator lights (`AttackStatBrush` yellow, `DefenseStatBrush` blue, `StaminaStatBrush` green), also theme brushes. Everything else app-specific — Pokémon type brushes (`{Type}TypeBrush`, looked up by name in `PokemonTypeToBrushConverter`), converters, `PokemonListItemTemplate`/`MoveListItemTemplate`/`TypeBadgeTemplate`, stat gauge templates, `DexListScrollViewerStyle` — lives in `Styles/AppResources.xaml`, merged after the Material theme in `App.xaml`. Its `ResourceDictionary.ThemeDictionaries` block must stay the *first* child: with it declared after the plain resources, Uno silently dropped every keyed resource in the file (templates resolved to null, rows rendered as type names). Use Material text styles (`TitleMedium`, `BodySmall`, …), theme brushes (`OnSurfaceBrush`, …) and `utu:CardContentControl` for cards; no hard-coded colours outside `App.xaml`'s seeds and the two style files.
- Pokémon artwork exists only for #1–151; `PokemonImages.GetUri` falls back to `unknown.png` for the rest.

### Code style

Formatting is enforced in CI (`Formatting` job) with `dotnet format whitespace` + `dotnet format style --verify-no-changes` against `DexUno.Modern/.editorconfig` (4-space C#, file-scoped namespaces, `System` usings first). `DexUno.Modern.Core/Entities/CpMultipliersMap.cs` is excluded from the whitespace check on purpose — it is a lookup table laid out several entries per line. XAML is *not* machine-formatted (XamlStyler cannot reproduce the hand-aligned attribute layout); keep new XAML in the style of its neighbours (2-space indent, aligned attributes). `dotnet format` only sees files compiled for the TFM it loads, so the wasm/Android/iOS build jobs re-run the two commands on the head to cover `Platforms/*`. Run locally before pushing (drop `--verify-no-changes` to auto-fix):

```bash
TargetFrameworkOverride=desktop dotnet format whitespace DexUno.Modern/DexUno.Modern.sln --verify-no-changes --exclude DexUno.Modern/DexUno.Modern.Core/Entities/CpMultipliersMap.cs
TargetFrameworkOverride=desktop dotnet format style DexUno.Modern/DexUno.Modern.sln --verify-no-changes
```

### CI, versioning and releases

- **CI/CD is GitHub Actions** (`.github/workflows/`), modelled on the DailyReflection repo's pipeline:
  - `ci.yml` — the merge gate for PRs and `master`: `Formatting`, `Build desktop (Skia)`, `Build WebAssembly`, `Build Android (unsigned)`, `Build iOS (simulator)`. The wasm and mobile jobs have two modes, switched by the workflow-level `RELEASE_BUILD` expression: for PRs into `master` and pushes to `master` they run the fast plain `dotnet build`; for builds *for* a `release/*` branch (a PR into one) they run the same publishes `release.yml` ships — wasm publish, Android arm64 Native AOT unsigned, iOS device Native AOT unsigned via `EnableCodeSigning=false`. Keep those publishes out of the everyday path (slow). The five job names are the intended required status checks on `master`; keep them stable.
  - `release.yml` — any push to a `release/*` branch: computes/validates the version, builds a signed `.aab`/`.apk` and `.ipa` (both **Native AOT**), self-contained desktop zips (win-x64 / linux-x64 / osx-arm64) and the wasm site (`-p:WasmShellWebAppBasePath=/DexUno/` + `.nojekyll`), then **waits for manual approval** on the `production` GitHub Environment before uploading to Google Play, uploading + submitting to App Store Connect (fastlane `deliver`), creating the GitHub release (which pushes the `vX.Y.Z` tag) and finally deploying the site to GitHub Pages (`deploy-web`, `github-pages` environment). `workflow_dispatch` inputs allow dry runs (Play test track, skip App Store review, skip the Pages deploy, `native_aot=false`).
  - `alpha.yml` — every merge to `master` that touches the modern app builds the same signed Native AOT packages and pushes them to the Play **internal** track and **TestFlight**; no approval gate because nothing it does is public. It is where trimming regressions surface first. Its build/signing steps mirror `release.yml`'s; change one, change the other.
  - Every job that builds the head pins itself with `env: TargetFrameworkOverride`, checks out with `fetch-depth: 0` (NBGV needs full history) and installs only its own workload.
- **Versioning is Nerdbank.GitVersioning** (`version.json` at the repo root; master carries `X.Y-alpha`, `publicReleaseRefSpec` = `release/*`). Cut release branches with `nbgv prepare-release`. NBGV's built-in mobile targets (`NBGV_SetVersionForMauiAndroid`/`IOS`) set the store versions during the build: Android `versionCode = major<<24 | minor<<16 | git height` (1.0.x ⇒ 16777216+x), iOS three-part `CFBundleVersion`/`CFBundleShortVersionString`. Do not hardcode `ApplicationVersion`/`ApplicationDisplayVersion` in the csproj, never switch to a scheme that produces smaller versionCodes once a release has shipped, and never re-run a release on the *same* commit — the stores reject a reused build number; push a commit instead.
- **Native AOT publish (what the stores get).** The `PublishAot` block in the csproj turns it on only for `dotnet publish` (`_IsPublishing`) on the `-android`/`-ios` TFMs; a plain `dotnet build`, Debug deploys and hot reload keep Mono/CoreCLR; desktop and wasm are excluded. Opt out per invocation with `-p:PublishNativeAot=false` (never pass `PublishAot` itself — as a global property it reaches `DexUno.Modern.Core` and fails with NETSDK1203). Reproduce locally: `dotnet publish DexUno.Modern/DexUno.Modern/DexUno.Modern.csproj -f net10.0-ios -c Release -r ios-arm64 -p:TargetFrameworkOverride=ios -p:EnableCodeSigning=false`, and `... -f net10.0-android -c Release -r android-arm64 -p:TargetFrameworkOverride=android` (needs NDK r27+). Uno's diagnostics: `-p:TrimmerSingleWarn=false -p:_ExtraTrimmerArgs=--verbose -p:IlcGenerateMetadataLog=true -p:IlcGenerateMstatFile=true`. The app has not shipped under Native AOT yet — bindings to types the trimmer cannot see render as empty controls, not crashes, so the first alpha build must be clicked through on a device.
- **Store identity**: `ApplicationId` `com.kazo0.dexuno` must match the `APP_ID` env in `release.yml`/`alpha.yml`. `Platforms/iOS/Info.plist` deliberately has no `CFBundleIdentifier`/`CFBundleVersion`/… — the iOS SDK fills them from the csproj (`$(...)` placeholders in a plist are *not* substituted). It declares `ITSAppUsesNonExemptEncryption=false` (offline app). Credentials live only in GitHub Actions secrets/variables (names listed in `docs/RELEASE-SETUP.md` §2); nothing is committed.
- `docs/RELEASE-SETUP.md` is the one-time setup checklist (store accounts, secrets, environments, rulesets, first-release sequence); `docs/privacy-policy.md` is the privacy-policy URL for the store listings.

Not carried over from the legacy app (by design): the accent-colour/picture-source Settings page, the separate global search page is now a section, and the Windows-only composition animations.

## Legacy app (`DexUno.sln`)

Data is bundled JSON (`DexUno/DexUno.Shared/Data/*.db.json`) plus per-Pokémon PNGs under `Assets/Flat/`. Last legacy commit is a "WIP Dual Screen" spike (Surface Duo / `TwoPaneView`).

Naming mismatch to be aware of: folders and project names are `DexUno.*`, but almost all C# namespaces are the legacy `Dex.Uwp.*` (shared UI) and `Dex.Core.*` (domain). Only `Startup`, `ServiceCollectionExtensions` and the platform heads use `DexUno.*`. Follow the existing namespace of the folder you're editing, not the folder name.

### Solution layout

- `DexUno.Core/` — netstandard2.0 class library, no UI dependencies. Entities (`Pokemon`, `Move`, `CpCalculator`, `TypeEffectiveness`…), data-source interfaces (`Dex.Core.DataAccess`), repositories and `TypesService`.
- `DexUno/DexUno.Shared/` — a **shared project** (`.shproj`/`.projitems`), not a class library. Every head compiles these sources directly, so a change here is rebuilt per head. Contains App, Shell, Pages, ViewModels, Cards/Controls/Partials (XAML user controls), Theme resource dictionaries, converters, services, and the JSON data.
- `DexUno/DexUno.{Droid,iOS,macOS,UWP,Wasm,Skia.Gtk,Skia.Wpf,Skia.Wpf.Host}/` — platform heads. Each imports `DexUno.Shared.projitems` and references `DexUno.Core`. Wasm/Gtk/Wpf heads also declare `UpToDateCheckInput` on the shared XAML so XAML edits trigger rebuilds.

### Build

There is no `global.json`; the repo uses whatever `dotnet` SDK is installed. Only the Core library builds cleanly on a current macOS/.NET 10 machine:

```bash
dotnet build DexUno.Core/DexUno.Core.csproj
```

The heads are legacy (netcoreapp3.1 for Gtk/Wpf, netstandard2.0 + `Uno.Wasm.Bootstrap` 2.0-dev for Wasm, classic Xamarin csproj for iOS/Android/macOS, UWP for Windows) and pin Uno `3.2.0` / `3.3.0-dev.99` packages. Known state on this machine (verified): `dotnet build DexUno/DexUno.Skia.Gtk/DexUno.Skia.Gtk.csproj` restores (slowly, ~9 min cold) but fails in `Uno.SourceGenerationTasks` with "Generation failed, error code 150" because the Uno 3.x source-generation host needs a .NET 5 runtime that isn't installed. Expect the same for Wasm/Wpf. iOS/Android/macOS/UWP heads need Visual Studio / Xamarin tooling (see `.vsconfig`). Don't burn time trying to make a head build unless the task is specifically about upgrading the toolchain.

`DexUno.Skia.Wpf.Host` references `..\DexUno.Skia.WPF\DexUno.Skia.WPF.csproj` with different casing than the real folder `DexUno.Skia.Wpf`; this only resolves on case-insensitive filesystems.

### Architecture

**Composition root.** `DexUno.Shared/Startup.cs` builds a plain `Microsoft.Extensions.DependencyInjection` container and exposes it as the static `Startup.ServiceProvider`. `App()` calls `Startup.Init()` before `InitializeComponent()`. Service location via `Startup.ServiceProvider.GetService<T>()` (extension in `ServiceCollectionExtensions`) is used throughout pages, the side pane, and even inside view models, alongside constructor injection.

**Interface + implementation in one file.** Services and repositories keep the interface and its implementation together in the `I*.cs` file (e.g. `INavigationService.cs` holds `NavigationService`, `IPokemonRepository.cs` holds `PokemonRepository`, `IJsonService.cs` holds `JsonService`). `grep` for `class Foo` will land you in `IFoo.cs`. Keep this convention.

**Page → ViewModel resolution is by naming convention.** All pages derive from `PageBase` (`Infrastructure/PageBase.cs`). On `OnNavigatedTo` it computes the VM type name from the page type: `Dex.Uwp.Pages.XyzPage` → `Dex.Uwp.ViewModels.XyzViewModel`, resolves it from the container via `Type.GetType`, calls `vm.OnNavigatedTo(e)`, and sets it as `DataContext`. Consequences:
- A new page needs a same-named `*ViewModel` in `Dex.Uwp.ViewModels`, subclassing `ViewModelBase`, or navigation throws.
- ViewModels are registered automatically: `AddViewModels()` reflects over every non-abstract `ViewModelBase` subclass in the assembly and registers it as transient. Never add them to `Startup` by hand.
- `[Bindable]` on VMs is required for Uno's reflection-free binding on non-UWP heads.

**Shell / navigation.** `Pages/Shell.xaml` is the window root: accent-colored command bar + `SplitView` with `SidePane` (hamburger menu) and a `Frame` (`MainFrame`). `NavigationService` (singleton) grabs that frame from `Window.Current.Content` and exposes one `NavigateToXPage()` method per page; `SidePane` maps menu labels to those methods in a hard-coded dictionary. Adding a page means touching `INavigationService.cs` and `SidePane.xaml.cs` as well.

`PageBase` also exposes `Title`, `RequiresAppBar` and a `Commands` collection of `ButtonBase`; `Shell` listens for `MainFrame.DataContextChanged` and, when the page loads, binds the title and moves the page's `Commands` into the shell's command bar.

**Data flow.** `LocalFileDataSource` (implements all four `I*DataSource` interfaces from Core) reads the bundled `ms-appx:///Data/*.db.json` files via `StorageFile` and deserializes with Newtonsoft (`JsonService`, enums as camel-case strings). Repositories (`PokemonRepository`, `MoveRepository`, `EvolutionsRepository`) lazily load and cache the whole list in memory on first call; they are registered transient, so each resolution re-reads the JSON. `TypesService` holds the type-effectiveness table and the 1.25 / 0.8 multipliers. Pokémon images are resolved by `IPokePicturesSource.GetPath(dexNumber)` → `ms-appx:///Assets/Flat/{n}.png` (surfaced to XAML through `PokemonDexNumberToPictureConverter`).

**Theming.** `App.xaml` merges `Theme/Brushes.xaml`, `Converters.xaml`, `Styles.xaml`, `Templates.xaml`. Converters are declared once in `Converters.xaml` and referenced by `StaticResource`. `ListItemTemplateSelector` / `MoveDetailTemplateSelector` pick `DataTemplate`s from application resources by key based on the item's CLR type (`Pokemon`, `QuickMove`, `ChargeMove`). The accent color is a user setting (`SettingsService`, stored in `ApplicationData.Current.LocalSettings`) and applied at startup by `ApplicationWindowManager`.

**Dual-screen WIP.** `PokedexPage.xaml` and `MovedexPage.xaml` wrap their content in `muxc:TwoPaneView`, with the list in pane 1 and the detail page (`PokemonDetailPage` / `MoveDetailPage`) embedded in pane 2 bound to a child VM the list VM resolves from the container. The Android head references `Uno.UI.DualScreen` and `Xamarin.DuoSdk` for this.

**Platform branches.** Use `#if WINDOWS_UWP` for UWP-only API shapes (see `Shell.xaml.cs`, `RectangularGauge.xaml.cs`, `IApplicationWindowManager.cs`); the Wasm head defines `WASM` in Debug.
