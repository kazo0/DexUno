# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

DexUno is a Pokémon GO pokedex app. The repo holds two generations of it side by side:

- `DexUno.Modern/` — the **current** app: an Uno Platform single-project app on the `Uno.Sdk` (`-dev` channel), .NET 10, Material theme, MVUX (Uno.Extensions.Reactive) with `FeedView`, Uno.Extensions navigation. Work here unless a task is explicitly about the legacy code. See "Modern app" below.
- `DexUno.sln` + `DexUno/` + `DexUno.Core/` — the **legacy** 2020-era port of the original UWP app ("Dex") to Uno 3.x. Kept for reference; it does not build on current tooling. See "Legacy app" below.

There are no tests and no CI in either.

## Modern app (`DexUno.Modern/`)

Layout:
- `DexUno.Modern.sln`, `global.json` (pins `Uno.Sdk`; bump the version there, never in csproj), `Directory.Packages.props` (central package management, currently empty because the Uno.Sdk supplies implicit packages).
- `DexUno.Modern.Core/` — net10.0 class library, no UI dependencies. `Entities` (records/classes shaped for `System.Text.Json`: `Pokemon`, `Move`→`QuickMove`/`ChargeMove`, `CombatStat`, `CP`, `CpCalculator`, `TypeEffectiveness`, `EvolutionLine`), `DataAccess/IPokedexDataSource` (the single abstraction over the bundled data), `Repositories` (singleton, lazily cached: Pokémon, moves, evolutions) and `Services/TypesService` (type chart, 1.25 / 0.8 multipliers).
- `DexUno.Modern/` — the Uno app. `Platforms/*` heads are template-generated; app code lives in `Presentation/` (pages + MVUX models + a few view-model partials), `Services/` (data source, image lookup), `Converters/`, `Styles/`, `Data/` (JSON, embedded resources), `Assets/Pokemon/` (256px PNGs for #1–151 plus `unknown.png`).

Build / run (from `DexUno.Modern/DexUno.Modern/`, always build a csproj from its own folder):

```bash
dotnet build -f net10.0-desktop          # Skia desktop (macOS/Linux/Windows) — the fast inner loop
dotnet run   -f net10.0-desktop          # launch it
dotnet build -f net10.0-browserwasm      # WebAssembly
dotnet build -f net10.0-ios / net10.0-android   # need the matching workloads
```

The `net10.0-windows10.0.26100` target only builds on Windows; the Uno.Sdk skips it elsewhere. Both desktop and wasm builds are verified clean on macOS. Restore of a new `-dev` Uno.Sdk version can take several minutes the first time. Uno Platform Studio / Hot Reload attach automatically in Debug through the DevServer.

Architecture:
- **Hosting & DI.** `App.xaml.cs` builds the Uno.Extensions host: logging, `ConfigureServices` (data source, repositories, `ITypesService`, all singletons) and `UseNavigation(ReactiveViewModelMappings.ViewModelMappings, RegisterRoutes)`. The mappings object is generated by MVUX and lets navigation instantiate the generated `*ViewModel` for a `*Model`. Models are resolved by the navigation framework, so their (record primary) constructors take services plus, for detail pages, the navigation data object.
- **Navigation is route/region based (Uno.Extensions).** Routes in `RegisterRoutes`: `""` (Shell) → `Main` (`MainPage`, the responsive shell) → nested visibility regions `Pokedex`, `Movedex`, `Types`, `Search`, `About`; plus root-level `PokemonDetail` and `MoveDetail` which are pushed on the frame from any region. `ViewMap`/`DataViewMap`/`FindByViewModel` all reference the **model** type (`PokedexModel`), never the generated view model. `MainPage.xaml` hosts a `NavigationView` (≥700px) and a bottom `TabBar` (<700px) that share the same `uen:Region.Name`s; the content grid with `Region.Navigator="Visibility"` must stay empty. Adding a section = page + model + `ViewMap` + `RouteMap` + one `NavigationViewItem` and one `TabBarItem`.
- **Detail pages take data via `DataViewMap`.** `PokemonDetailModel(Pokemon?, …)` and `MoveDetailModel(MoveSelection?, …)`. `MoveSelection` is a sealed wrapper because moves are polymorphic and route/data matching is by type; keep using it rather than passing `Move` directly. Navigate from a model with `Navigator.NavigateViewModelAsync<TModel>(this, data: …, cancellation: ct)`.
- **Master/detail on wide screens.** `PokedexPage`/`MovedexPage` code-behind watch their own width (≥900px → `Wide` visual state and `vm.Model.SetWideLayout(true)`). The list model owns a child `PokemonDetailModel`/`MoveDetailModel` (`DetailModel`, created with a null initial item so its `Current` state starts empty). When wide, selecting an item calls `DetailModel.Show(...)` and the pane shows it through the shared `PokemonDetailView`/`MoveDetailView` user controls; when narrow, selection navigates to the detail page. The MVUX generator exposes nested models as raw pass-throughs, so `PokedexViewModel.cs`/`MovedexViewModel.cs` are hand-written partials of the generated view models that expose a bindable `Detail` built through the generated `protected XViewModel(XModel)` constructor (`PokemonDetailViewModel.For(...)`). Those partials carry `[ReactiveBindable(false)]` because their names end in `Model` and would otherwise be treated as models themselves. This replaces the legacy `TwoPaneView` dual-screen spike.
- **MVUX.** `UnoFeatures` includes `MVUX`; no CommunityToolkit.Mvvm. Every page has a `partial record XxxModel` whose services come in as record primary-constructor parameters; the generator emits `XxxViewModel` (what the page's `DataContext` actually is) with a `Model` property. Async data is exposed as `IFeed<T>`/`IListFeed<T>` (`Feed.Async`, `ListFeed.Async`, `state.Select/SelectAsync`, `Feed.Combine(...)...AsListFeed()`), user input as `IState<T>` (`State.Value(this, () => …)`, two-way bound; update with `UpdateAsync`), and public methods become `IAsyncCommand`s of the same name (`ToggleSortDirection`, `SelectPokemon(Pokemon, ct)` → item is the command parameter). Read a feed's current value with `await SomeFeed`. Nothing loads in constructors; feeds load when the view subscribes. Records like `PokemonDetails`/`MoveDetails` carry what a detail view shows; a feed's `null` result or an empty list feed is the `None` state. Avoid naming anything that is not a model with a `Model` suffix.
- **Lists are ItemsRepeaters, and the long ones are paginated.** No `ListView` anywhere: every list is an `ItemsRepeater` inside a `ScrollViewer` (`DexListScrollViewerStyle`), with `utu:ItemsRepeaterExtensions.SupportsIncrementalLoading="True"` where the feed is paginated, `utu:ItemsRepeaterExtensions.SelectionMode`/`SelectedItem` for the master lists' highlight (two-way bound to a `Selected` state on the model) and `utu:CommandExtensions.Command` for the tap action. Selection visuals need the item template's root to be a `ListViewItem` (or another `SelectorItem`/`ToggleButton`) — that is why `PokemonListItemTemplate`/`MoveListItemTemplate` wrap their row in one; the toolkit sets `IsSelected` itself, don't bind it.
  Paginated feeds: `PokedexModel.Items`, `MovedexModel.Items`, `SearchModel.Results` and `MoveDetailModel.UsedBy` (a common move has a hundred users, and it pages in as the detail view is scrolled). Each is `<source feed>.SelectPaginatedAsync<…, T>((value, page, ct) => …)`, slicing a cached filtered/sorted list with `page.CurrentCount`/`page.DesiredSize` (`DefaultPageSize` only covers the first page, where `DesiredSize` is null), and restarts from page 1 whenever the source value — search text, sort, tab, current move — changes. The private `MatchesAsync`/`UsersAsync` caches exist so a page request is a slice, not a re-query. The Types list (18 cards) is an `ItemsRepeater` without pagination.
  The scroller keeps its offset when the criteria change, which would leave a shorter result set rendering as blank space, so `PokedexPage`/`MovedexPage`/`SearchPage` capture the `ScrollViewer` from inside the FeedView template (`Loaded`) and scroll it back to the top from the search / tab / reverse-order handlers.
- **FeedView everywhere.** All async content is rendered through `mvux:FeedView Source="{Binding SomeFeed}"` (`xmlns:mvux="using:Uno.Extensions.Reactive.UI"`). Inside its templates the `DataContext` is the `FeedViewState`: bind values as `{Binding Data.…}`, commands as `{Binding Parent.SomeCommand}`, and reach the view model from nested item templates with `{Binding DataContext.SomeCommand, ElementName=<named root>}`. `NoneTemplate` is used for empty lists, the blank search query and the unselected master/detail pane. The loading visual is the animated pokeball `PokeballLoader` user control (a vector copy of `unknown.png` with a wobble/button-flash storyboard): an implicit `FeedView` style in `AppResources.xaml` sets it as every `ProgressTemplate`, and the splash screen in `Shell.xaml` uses it too, so never add a `ProgressRing`. `Shell.xaml` sets `ExtendedSplashScreen.Platforms="None"` so the toolkit does not replicate the native splash image/colour: the extended splash is just the centred pokeball on `BackgroundBrush`. List item taps are wired with `utu:CommandExtensions.Command` on the `ItemsRepeater` (item = command parameter), never in code-behind. Inside a `NoneTemplate`, `{Binding Parent.…}` does not resolve — reach the view model through the page's named root instead (`{Binding DataContext.SearchText, ElementName=Root}`, as `SearchPage` does for its two empty states).
- **Data.** `Data/*.json` are `EmbeddedResource`s (`Data.<name>.json`) read by `EmbeddedJsonPokedexDataSource` through a source-generated `PokedexJsonContext` (case-insensitive, string enums). Type chart JSON keys are the attacking type; `strengths`/`weaknesses` map to `StrongAgainst`/`WeakAgainst`.
- **Theme & resources.** Material 3 palette in `Styles/ColorPaletteOverride.xaml` (red primary carried over from the original accent). Everything app-specific — Pokémon type brushes (`{Type}TypeBrush`, looked up by name in `PokemonTypeToBrushConverter`), stat brushes, converters, `PokemonListItemTemplate`/`MoveListItemTemplate`/`TypeBadgeTemplate`, stat gauge templates, `DexListScrollViewerStyle` — lives in `Styles/AppResources.xaml`, merged after the Material theme in `App.xaml`. Use Material text styles (`TitleMedium`, `BodySmall`, …), theme brushes (`OnSurfaceBrush`, …) and `utu:CardContentControl` for cards; no hard-coded colours outside `AppResources.xaml`.
- Pokémon artwork exists only for #1–151; `PokemonImages.GetUri` falls back to `unknown.png` for the rest.

Not carried over from the legacy app (by design): the accent-colour/picture-source Settings page, the separate global search page is now a section, and the Windows-only composition animations.

## Legacy app (`DexUno.sln`)

Data is bundled JSON (`DexUno/DexUno.Shared/Data/*.db.json`) plus per-Pokémon PNGs under `Assets/Flat/`. Last legacy commit is a "WIP Dual Screen" spike (Surface Duo / `TwoPaneView`).

Naming mismatch to be aware of: folders and project names are `DexUno.*`, but almost all C# namespaces are the legacy `Dex.Uwp.*` (shared UI) and `Dex.Core.*` (domain). Only `Startup`, `ServiceCollectionExtensions` and the platform heads use `DexUno.*`. Follow the existing namespace of the folder you're editing, not the folder name.

### Solution layout

- `DexUno.Core/` — netstandard2.0 class library, no UI dependencies. Entities (`Pokemon`, `Move`, `CpCalculator`, `TypeEffectiveness`…), data-source interfaces (`Dex.Core.DataAccess`), repositories and `TypesService`.
- `DexUno/DexUno.Shared/` — a **shared project** (`.shproj`/`.projitems`), not a class library. Every head compiles these sources directly, so a change here is rebuilt per head. Contains App, Shell, Pages, ViewModels, Cards/Controls/Partials (XAML user controls), Theme resource dictionaries, converters, services, and the JSON data.
- `DexUno/DexUno.{Droid,iOS,macOS,UWP,Wasm,Skia.Gtk,Skia.Wpf,Skia.Wpf.Host}/` — platform heads. Each imports `DexUno.Shared.projitems` and references `DexUno.Core`. Wasm/Gtk/Wpf heads also declare `UpToDateCheckInput` on the shared XAML so XAML edits trigger rebuilds.

### Build

There is no `global.json`; the repo uses whatever `dotnet` SDK is installed. Only the Core library builds cleanly on a current macOS/.NET 10 machine:

```bash
dotnet build DexUno.Core/DexUno.Core.csproj
```

The heads are legacy (netcoreapp3.1 for Gtk/Wpf, netstandard2.0 + `Uno.Wasm.Bootstrap` 2.0-dev for Wasm, classic Xamarin csproj for iOS/Android/macOS, UWP for Windows) and pin Uno `3.2.0` / `3.3.0-dev.99` packages. Known state on this machine (verified): `dotnet build DexUno/DexUno.Skia.Gtk/DexUno.Skia.Gtk.csproj` restores (slowly, ~9 min cold) but fails in `Uno.SourceGenerationTasks` with "Generation failed, error code 150" because the Uno 3.x source-generation host needs a .NET 5 runtime that isn't installed. Expect the same for Wasm/Wpf. iOS/Android/macOS/UWP heads need Visual Studio / Xamarin tooling (see `.vsconfig`). Don't burn time trying to make a head build unless the task is specifically about upgrading the toolchain.

`DexUno.Skia.Wpf.Host` references `..\DexUno.Skia.WPF\DexUno.Skia.WPF.csproj` with different casing than the real folder `DexUno.Skia.Wpf`; this only resolves on case-insensitive filesystems.

### Architecture

**Composition root.** `DexUno.Shared/Startup.cs` builds a plain `Microsoft.Extensions.DependencyInjection` container and exposes it as the static `Startup.ServiceProvider`. `App()` calls `Startup.Init()` before `InitializeComponent()`. Service location via `Startup.ServiceProvider.GetService<T>()` (extension in `ServiceCollectionExtensions`) is used throughout pages, the side pane, and even inside view models, alongside constructor injection.

**Interface + implementation in one file.** Services and repositories keep the interface and its implementation together in the `I*.cs` file (e.g. `INavigationService.cs` holds `NavigationService`, `IPokemonRepository.cs` holds `PokemonRepository`, `IJsonService.cs` holds `JsonService`). `grep` for `class Foo` will land you in `IFoo.cs`. Keep this convention.

**Page → ViewModel resolution is by naming convention.** All pages derive from `PageBase` (`Infrastructure/PageBase.cs`). On `OnNavigatedTo` it computes the VM type name from the page type: `Dex.Uwp.Pages.XyzPage` → `Dex.Uwp.ViewModels.XyzViewModel`, resolves it from the container via `Type.GetType`, calls `vm.OnNavigatedTo(e)`, and sets it as `DataContext`. Consequences:
- A new page needs a same-named `*ViewModel` in `Dex.Uwp.ViewModels`, subclassing `ViewModelBase`, or navigation throws.
- ViewModels are registered automatically: `AddViewModels()` reflects over every non-abstract `ViewModelBase` subclass in the assembly and registers it as transient. Never add them to `Startup` by hand.
- `[Bindable]` on VMs is required for Uno's reflection-free binding on non-UWP heads.

**Shell / navigation.** `Pages/Shell.xaml` is the window root: accent-colored command bar + `SplitView` with `SidePane` (hamburger menu) and a `Frame` (`MainFrame`). `NavigationService` (singleton) grabs that frame from `Window.Current.Content` and exposes one `NavigateToXPage()` method per page; `SidePane` maps menu labels to those methods in a hard-coded dictionary. Adding a page means touching `INavigationService.cs` and `SidePane.xaml.cs` as well.

`PageBase` also exposes `Title`, `RequiresAppBar` and a `Commands` collection of `ButtonBase`; `Shell` listens for `MainFrame.DataContextChanged` and, when the page loads, binds the title and moves the page's `Commands` into the shell's command bar.

**Data flow.** `LocalFileDataSource` (implements all four `I*DataSource` interfaces from Core) reads the bundled `ms-appx:///Data/*.db.json` files via `StorageFile` and deserializes with Newtonsoft (`JsonService`, enums as camel-case strings). Repositories (`PokemonRepository`, `MoveRepository`, `EvolutionsRepository`) lazily load and cache the whole list in memory on first call; they are registered transient, so each resolution re-reads the JSON. `TypesService` holds the type-effectiveness table and the 1.25 / 0.8 multipliers. Pokémon images are resolved by `IPokePicturesSource.GetPath(dexNumber)` → `ms-appx:///Assets/Flat/{n}.png` (surfaced to XAML through `PokemonDexNumberToPictureConverter`).

**Theming.** `App.xaml` merges `Theme/Brushes.xaml`, `Converters.xaml`, `Styles.xaml`, `Templates.xaml`. Converters are declared once in `Converters.xaml` and referenced by `StaticResource`. `ListItemTemplateSelector` / `MoveDetailTemplateSelector` pick `DataTemplate`s from application resources by key based on the item's CLR type (`Pokemon`, `QuickMove`, `ChargeMove`). The accent color is a user setting (`SettingsService`, stored in `ApplicationData.Current.LocalSettings`) and applied at startup by `ApplicationWindowManager`.

**Dual-screen WIP.** `PokedexPage.xaml` and `MovedexPage.xaml` wrap their content in `muxc:TwoPaneView`, with the list in pane 1 and the detail page (`PokemonDetailPage` / `MoveDetailPage`) embedded in pane 2 bound to a child VM the list VM resolves from the container. The Android head references `Uno.UI.DualScreen` and `Xamarin.DuoSdk` for this.

**Platform branches.** Use `#if WINDOWS_UWP` for UWP-only API shapes (see `Shell.xaml.cs`, `RectangularGauge.xaml.cs`, `IApplicationWindowManager.cs`); the Wasm head defines `WASM` in Debug.
